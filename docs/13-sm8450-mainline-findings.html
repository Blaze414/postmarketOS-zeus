SM8450 · Xiaomi 12 Pro (zeus) · audio findings

The TDM sink never pulls

On this board the speaker path ends at a hardware endpoint that the DSP configures correctly and then never feeds. The same wall has now been reached twice from opposite directions — through mainline’s in-kernel q6apm, and through Qualcomm’s own AudioReach userspace driving the same firmware. Three side findings along the way look independently useful to this tree.

Kernel

The symptom, precisely

Captured the ADSP’s F3/QShrink diag across a playback attempt on both backends, on one loaded topology, and compared them directly. 

headphones, CODEC_DMA sink (module 0x6072)
  line=195  args=[<cont>, 0x6001, 0x0, 0x5001004, <buf>, 0x20, ...]   x12
  the write-shmem EP completing buffers as the sink pulls
  bufdone = 12    underrun = 0    media_format_set = 1

speakers, TDM sink (module 0x60a2)
  line=1127 args=[<cont>, 0x60a2, 0x2, 0x3e8, 0x30, 0xbb80, 0xc0]      x1
  2 ch, 48000 Hz, 48 samples/ms, 192 bytes/ms — computed correctly
  bufdone = 0     underrun = 27   media_format_set = 0

The endpoint’s hardware media format is right. Its input data port never receives a stream media format, so it never pulls, and no buffer ever reaches it. The TDM sink runs its own 1 ms timer, which is where the periodic underruns come from. A structurally identical codec-DMA graph flows normally, and disassembly of both sinks’ CAPI_INPUT_MEDIA_FORMAT_V2 handlers shows byte-identical acceptance checks — the TDM sink is not rejecting a format, it is never offered one.

Confirmed from the other side

To test whether this is mainline’s graph handling or the firmware itself, the vendor userspace was brought up on postmarketOS: a small audio_pkt character device over the existing GPR router, plus Qualcomm’s audioreach-graphservices (GSL) built against musl, driving graphs straight out of the phone’s own ACDB. Shared memory comes from dma_alloc_coherent() against a node carrying iommus = <&apps_smmu 0x1801 0x0>, which lands in the same IOMMU group as q6apmdai.

That path gets a long way. With the stock speaker use case (a1000000=a1000005 a2000000=a2000001 ac000000=ac000003, four subgraphs, both WR_SHMEM_EP and TDM_SINK):

Three findings worth checking upstream

These came out of the userspace work but are about this tree, not about GSL.

Finding 1 · graph start order

A device subgraph will not start before its source is running

GSL sends APM_CMD_GRAPH_START with the whole subgraph list in graph order, device first. Every device subgraph refuses it — b0000002 (speakers) and b0000014 (headphones) alike. Starting them one at a time from the far end back, so each subgraph starts only once its source is live, every one succeeds: 

GSL_START_ONLY_SG=3  b000000e  OK      GSL_START_ONLY_SG=1  b000000f  OK
GSL_START_ONLY_SG=2  b0000020  OK      GSL_START_ONLY_SG=0  b0000002  OK   <- speakers

Started first instead, b0000002 is refused with a bare AR_EFAILED. The DSP-side message that fires only in the failing case reports a module in that subgraph with its media-format flags still clear.

Worth a look at audioreach_graph_start(), which likewise sends the whole subgraph list in one command. It has not been shown to misbehave here — the speaker path fails for its own reasons long before this matters — but the ordering constraint appears to be real.

Finding 2 · ADSP restart

The sound card does not survive an ADSP restart

Cycling /sys/class/remoteproc/remoteproc1/state brings the DSP back cleanly, but the card does not come with it: 

wcd938x_codec audio-codec: ASoC: error at snd_soc_component_probe on audio-codec: -16
snd-sc8280xp sound: ASoC: failed to instantiate card -16

-EBUSY from the codec component on re-probe; only a reboot recovers it. Reproducible, and independent of anything in this report.

Finding 3 · boot-time timeout

q6apm’s SPF state query times out while userspace’s answers instantly

Every boot logs qcom-apm gprsvc:service:2:1: CMD timeout for [1001021] opcode about five seconds in. The identical APM_CMD_GET_SPF_STATE sent from userspace over the same router is answered immediately: 

tx  00001860 00000302 00002003 00000001 5a5a0001 01001021
rx  00001c60 00000203 00000001 00002003 5a5a0001 02001007 00000001
                                                          ^ SPF ready

So the DSP is not slow to answer. Something about how the in-kernel client waits misses the reply. Harmless in practice — q6apm retries — but it suggests a real race.

One caveat worth stating plainly: the vendor ACDB’s calibration key-vector tables fail to parse in current graphservices (AR_ENEEDMORE), and no persistent calibration is found for b0000002 or b0000006. Only one database file is loaded where Android loads several. Whether that matters to the endpoint is untested.

Where the reasoning stops

The DSP’s own explanation is out of reach. SPF messages are QShrink-hashed, and the only database on the phone is the modem’s — none of the relevant hashes appear in it, in either byte order. The ADSP’s database is generated when the firmware is built and is not shipped.

Hashes can still be attributed to source files by locating the 12-byte descriptor {ssid<<16|line, ss_mask, hash} in adsp.mbn and reading the code that references it. Hexagon assembles a 32-bit constant from an extender plus the following instruction, so the address is never four contiguous bytes; the extender carries imm[31:6], which narrows a search to 64 bytes: 

0000 | imm[31:20] (bits 27-16) | parse (bits 15-14) | imm[19:6] (bits 13-0)

call sites then look like:
  immext(##0xb090d140)
  R1:0 = combine(#0x4,##0xb090d160)   ; R0 = descriptor, R1 = argc
  call 0xb0030b20                     ; logging entry point

The messages around the failure attribute to Spf’s gen_topo set — the generic topology layer that starts modules. Recovering the actual condition means reading a few thousand lines of hashed Hexagon assembly, which is where this stops.

Reproducing it

The kernel-side symptom needs only this tree plus a topology with a tertiary TDM playback backend; play anything at the speaker PCM and watch the ADSP diag for media_format_set staying at 0 while underruns climb.

Packet-level comparison is easier with a tap in the router itself, since q6apm, q6prm and any userspace client all pass through pkt_router_send_svc_pkt() and gpr_do_rx_callback(): 

echo 1 > /sys/module/apr/parameters/gpr_trace   # local patch, off by default
dmesg -C                                        # the touchscreen driver floods
                                                # the ring buffer in seconds
<run the case>
dmesg | grep -E 'gpr tx|gpr rx'

Patches, the audio_pkt shim, the GSL build for musl and the QShrink attribution tools are in github.com/YusufAlZadid’s zeus port tree and can be split out into whatever form is useful.
